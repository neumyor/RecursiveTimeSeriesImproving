# G0 重测清单与 main-v3 重跑方案

依据：norms-stage-1 至 stage-5 的代码修复（见 docs/norms-review-findings.md 第一节）。本文档只给方案，不运行任何实验；启动由用户亲自触发。

## 一、哪些既有结果失效，哪些仍可用

### 失效，必须重测

| 结果 | 失效原因 | 受影响的修复 |
|---|---|---|
| **p2-3seed 全部数据**（16 个跑满、10 个部分、8 个空目录） | 智能体看到的反馈本身就是错的：hgroup[13,24] 的数值切错了轴（所有实验组）；探针输出在 600 字符处被截断；历史表只有最近 10 轮；连续拒绝时每轮调用多样性判定。认证结论偏向"饱和"（见下行）。这些改变了智能体的输入，旧数据回答的是另一个实验。 | 第一节条目 1、5、12 |
| **G0-2**（CI 校准）、**G0-3+4**（紧致度与定位）、**G0-5**（误停率）、**G0-6**（筛选）两个报告的全部数值 | 贪心选择里候选缺少截距，残差均值非零时少选甚至不选，total 与 hgroup 的认证统计量被系统性压低；通道坐标的 lag 窗口从 25 个改为 24 个，改变了通道块的构造。两处都改变了修正器的拟合，进而改变所有依赖修正器增益的门控数值。 | 条目 2、14 |
| **CAL1-3**（校准） | 同上，CAL-1 直接使用贪心 total 增益，CAL-2、CAL-3 使用认证 | 条目 2、14 |
| 已冻结报告 `g0-final-report-v3.json` 与 `g0-final-report-v3-deep.json`（两个文件） | 是上面各项结果的快照；`main-v3.json` 引用它们作为 G0 依据，修订段落已说明"测于修复之前" | — |

### 仍然可用

| 结果 | 理由 |
|---|---|
| **G0-1**（oracle 负对照）、**G0-7**（观测 0 的解析对照） | G0-1 用 oracle 当模型，残差只有噪声，不经过贪心选择的候选打分；G0-7 是纯 AR(1)/白噪声的解析对照，不经过修正器。两者在结构上与截距和 lag 窗口无关。**建议仍在重测时顺带复核**——成本是几分钟，因为 `stage0.py` 一次跑完全部七个门控。 |
| 合成任务的 oracle、数据生成、夹具注册表、探针契约、`m0` 与 `m0_deep` 模板 | 阶段 1-5 没有改变这些；synthetic.py 只改了"读取配置的方式"，默认配置下输出逐位相同（子智能体验证过）。 |
| 阶段 2 以后的代码重构（evaluate 合并、重复检查收敛） | 行为保持的重构，有现有测试作为等价证据。 |

## 二、main-v3 重跑

**范围**：`experiments/specs/main-v3.json`，4 任务 × 4 实验组 × 3 种子 = 48 个单元格，每格 25 轮。真实任务 real-ett 与 3 个合成任务共用同一个批处理。

**时长**：p2-3seed 的实测数据——已完成单元格中位 7.2 小时、最长 10.1 小时（scalar 6.2、fixed 5.9、augmented 7.2、self-built 9.3 小时中位）。单元格耗时主要是 LLM 往返与候选训练，并发度高时线性缩短，直到 LLM 网关限流或 CPU 饱和。

**并发与资源**：
- 机器：**本机**（macOS，10 核 / 16 GB）。理由：LLM 网关（llm-center.modelbest.co）本机直连；REMOTE_SERVER.md 记录的远端是另一个项目的共享机器，直连 LLM 超时，需要本地中继加反向隧道，且 API key 路径与共享环境耦合，对本实验是纯增加复杂度。用户对复杂度的明确偏好也指向本机。
- 并发度：每个单元格是一个 `loop.py` 进程，内含候选训练（torch，已 pin 为单线程）。本机 10 核建议 `--workers 6`（预留两核给 LLM 往返与系统）；预计 48/6 = 8 批，总时长约 8 × 7.2 ≈ **58 小时**（上界 8 × 10 = 80 小时）。`--workers 8` 可压到约 43-60 小时，内存 16 GB 下深度模型（PatchTST-lite）并发训练 8 个有风险，**不建议超过 6**，除非先实测内存。
- 断点续跑：batch 以 heldout 侧 `done.json` 判定完成，中断后同命令重启自动跳过已完成单元格；单元格内以 `rounds.jsonl` 台账续跑（修复后的恢复逻辑已含台账先行与孤立记录回收，由测试覆盖）。
- 前端：实验页可直接监控、启动、停止（`/experiments`）。

**重跑前必须先完成**：重测 G0（`uv run python experiments/stage0.py` 与 `--deep`）并冻结新版报告——`main-v3.json` 的 `schemaVersion >= 2` 门要求 g0-final-report-v3 与 v3-deep 两个工件存在，重测后若判定通过、结论仍是"全部 PASS"，沿用文件名覆盖前先把旧版另存；若有门控翻转（尤其 G0-5 误停率、G0-3+4 定位率），需要先判断是否影响 P2 任务列表（G0-6 筛选的三个任务 hmm_ar_switch、nonlinear_xchannel、lgssm_xchannel 是否仍有足够的残余可改进空间）。

## 三、重跑前后的一致性检查

对齐 AGENTS.md 的"先注册再看结果""必须在留出集复核"：

**重跑前（注册）**
1. 重测 G0 后立即冻结报告并提交（commit 即注册）；在看到任何 P2 单元格结果之前完成。
2. `main-v3.json` 的修订段落要在 G0 重测结果出来后补一句"G0 门控已于 <日期> 在修复后重测，结果 <通过/变化>"，随提交冻结；任务、实验组、种子、预算不改。
3. 记录本机环境（Python、torch、numpy 版本）与 LLM 配置（模型名、`maxTokens`），写进运行目录的说明文件，用于事后复现说明。
4. 矩阵开跑后 30 分钟内粗检：取最早几个单元格第 1-2 轮的产物，核对 rounds.jsonl 字段完整、heldout 记录三件套（certification、acceptances、done 的形态）齐全、posthoc 卡片逐轮存在、反馈里 hgroup[13,24] 数值与重算一致、探针/历史/错误输出不被截断、判定 reason 通过泄漏过滤。粗检不过立即停矩阵、修复后按 done.json 台账续跑。

**重跑中**
5. 每个单元格完成时自动落盘；批处理遇到连续失败会中止（`SystemicFailure` 的中止路径此前从未真正生效，现已修复并有测试）——中止后先查原因（账户余额、网关）再续跑。
6. 不在中途修改代码、提示词或规格；如必须修改，按"协议变化"处理——新规格版本，已跑单元格是否作废由变更内容决定（改动影响智能体输入则作废）。

**重跑后（留出集复核）**
7. `posthoc.py` 对完整运行目录生成 `analysis.json`（前端"生成分析"按钮或命令行）；检查 `incomplete` 为空、`audit` 路径违规为 0、`gainRatioFlags` 记录在案。
8. 论文数字只取 `analysis.json` 的 endpointTable 与 contrasts（留出的测试段上的 incumbent 终点指标），不取前端的逐轮诊断段 MSE；诊断段 MSE 是智能体选择候选时看到的数据，不是论文结论的依据。
9. 对失败或部分完成的单元格按规格的预注册处理（计入失败率，不事后剔除）。

## 四、建议的执行顺序

1. **G0 重测**（本机，`stage0.py` 全量加 `--deep`；预计数小时，G0-3+4 和 G0-6 最耗时）→ 比对新旧报告，写差异说明，冻结新版并提交。——先于一切，因为它决定任务列表是否成立。
2. **放开全矩阵**（G0 报告冻结并提交之后；`--workers 6`，从前端实验页或命令行启动）→ 约 58 小时，可监控，可随时停止续跑；开跑后 30 分钟内按第三节第 4 条粗检。
3. （原冒烟步骤取消：粗检用矩阵最早的第 1-2 轮产物，覆盖同样的内容，门槛低两个数量级。）
4. **posthoc 分析 + 论文数字提取**。

已裁决：(a) G0 重测若出现门控翻转，先停下报告，不自行改任务列表；分两种情形——数值变化可由修复本身（缺截距、lag 25→24）解释的，属预期内的口径变化，新旧数值并列并给出判断，按协议变化处理；无法解释或某门从 PASS 变 FAIL 的，先按 bug 查，查不出再报。无论哪种，不增删任务，不事后调整 G0-6 的筛选阈值。(b) 不跑单格冒烟，按上面的 30 分钟粗检执行。
