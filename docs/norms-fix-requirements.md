# 仓库修复需求与实施方案

用户于 2026-10-18 确认。整个修复过程以本文件为准，每个阶段结束时对照检查。

## 需求

**要完成的事**

1. 修复静态评审报告第一节（影响论文实验结论的错误）。
2. 修复第三节（哈希、重复检查、过度设计和兼容代码）、第四节（重复实现）、第五节（修改痕迹）。
3. 修复第二节（交互系统的后端和前端功能错误）。
4. 把实验系统接入前端：在前端启动实验，并查看运行过程。
5. 用 git 管理版本，每个阶段都能单独回退。

**约束**

- 只修改代码，不运行实验。`uv run pytest` 和前端构建属于检查，照常运行。
- 删除全部兼容代码，包括 V0-V6 变体别名和 `/api/live`，同步修改 AGENT.md 和 README.md。
- 遵守 behavior-norms：不加哈希或校验，不重复检查，不过度设计；注释只描述当前行为；送给 LLM 的输入不截断。
- 第一节的每条修复只做最小的行为变更，并配测试验证。
- 有取舍的条目选保守做法，例如让显式的 `--m0-template` 参数生效，不删除接口。
- 每条修复的问题编号、根因和验证证据写在提交说明里，不写进代码注释。
- 不提交 `.dsh-sessions/`、`REMOTE_SERVER.md` 和 `docs/` 下其他未跟踪的文件。
- 阶段 1 结束后停下，向管理者会话（"Claude Code 管理员"）汇报：修复清单、需要重跑的已冻结结果和 G0 门控、对 p2-3seed 的影响评估。

**已知影响**

- 第一节的修复会改变智能体看到的反馈和认证结论。`main-v2.json` 规定第一次 v2 运行之后的协议变化需要新规格版本，因此新建 `main-v3.json`，`experiments/runs/p2-3seed` 保持原样。
- 截距错误修复后，已冻结的 G0-v3 报告和当前代码不再一致。按用户要求不重新运行。

## 实验系统接入前端的流程

| 步骤 | 输入 | 输出 | 前端展示 |
|---|---|---|---|
| 1. 选择规格 | `experiments/specs/` 下的规格文件 | 单元格列表（任务 × 实验组 × 种子）和轮次预算 | 规格下拉框；单元格矩阵预览 |
| 2. 启动批量运行 | 规格、运行名称、并发数、单元格筛选条件 | 后台 batch 进程；`batch-status.jsonl`；单元格日志 | 启动和停止按钮；进程状态；batch 日志最后 200 行 |
| 3. 单元格运行 | `loop.py` 执行每个单元格 | `rounds.jsonl`；heldout 目录（认证、接受记录、posthoc 卡片、`done.json`） | 矩阵视图：已完成轮数/预算、接受次数、当前 incumbent、是否饱和、是否失败 |
| 4. 单元格详情 | 选中的单元格 | 同上 | 每轮表格；incumbent MSE 折线图；认证时间线；提案全文 |
| 5. 智能体过程 | `ws/logs/round-N.jsonl` | 每轮的消息和工具调用 | 复用现有对话渲染组件，按轮次切换 |
| 6. 汇总分析 | 运行目录 | `analysis.json` | "生成分析"按钮；各实验组对比表 |

- 页面打开期间每 5 秒请求一次运行状态。
- 每个运行名称同时只有一个 batch 进程。进程号写入 `runs/<名称>/batch-process.json`，服务重启后据此恢复状态。停止时向进程组发送 SIGTERM，下次启动跳过已完成的单元格。
- 单个单元格用 batch 的筛选条件 `cell=<单元格名>` 启动。
- 规格只能从 `experiments/specs/*.json` 中选择；运行名称只允许字母、数字、`.`、`_`、`-`。

## 实施方案

**版本管理**

- 分支 `fix/norms-review`，起点标签 `norms-base`。
- 每个逻辑完整的修复单独提交。子智能体不提交，由主智能体检查后提交。
- 每个阶段检查通过后打标签 `norms-stage-N`。回退整个阶段用 `git reset --hard norms-stage-(N-1)`，回退单个修复用 `git revert <提交>`。

**阶段**

1. 第一节的错误（报告见 docs/norms-review-findings.md 第一节，含 13 条主条目和 4 条补充条目）。3 个子智能体同时进行：A 负责 `headroom/`，B 负责 `experiments/loop.py` 和 `experiments/prompts/`，C 负责 `experiments/` 下其余文件。`rounds.jsonl` 和 heldout 目录的字段结构不变。完成标准：`uv run pytest -q` 全部通过。结束后向管理者会话汇报。条目编号（提交说明使用）：
   - A1→报告条目 2（截距）；A2→条目 14（lag 窗口）；A3→条目 15（synthetic 默认配置）；A4→条目 16（表格转义）；A5/A6→条目 12（截断上限：探针输出、错误输出）；B1→条目 1（hgroup 切轴）；B2→条目 4（计时）；B3→条目 5（判定触发）；B4→条目 6（原地修复）；B5→条目 12（历史轮数）；B6→条目 11a（heldout 重建）；B7→条目 11b（写入顺序）；B8→条目 10（家族数量）；C1→条目 3（batch 取消）；C2→条目 7（比例）；C3→条目 8（--m0-template）；C4→条目 11c（未完成运行）；C5→条目 13（judgeAccounting）；C6→条目 9（stage0 继承）；C7→条目 17（fixture_gen 门控）；C8→规格版本化的必然结果（新建 main-v3.json）。
   - 以下子智能体顺手完成的条目属于第三至五节，阶段 1 的提交和标签不包含它们，留到阶段 2 提交：A7-A10（docstring 位置、certify level 残留、实验组数量注释、synthetic 注释）、B9-B11（测试写入主目录、loop docstring 与修改痕迹、_evolution_digest 改名）、C9-C11（stage0 冒烟测试写入仓库、docstring 位置、修改痕迹）。
2. `headroom/` 和 `experiments/` 中属于第三、四、五节的问题，包括把重复的拟合预测流程集中到 `evaluate.py`。
3. 后端核心模块中属于第三、四、五节的问题。3 个子智能体同时进行：D 负责控制流模块，E 负责知识、状态和设置模块，F 负责服务入口、测试、脚本和文档。开始前由主智能体写好 `settings/llm.py` 中的 `sanitize_llm_config`。完成标准：`pytest` 通过，`uv run ts-harness variants` 正常输出。
4. 第二节的问题，以及 `main.ts` 中属于第三至五节的问题。G 负责后端，H 负责前端。后端遇到 SDK 错误结果时在公开字段中设置 `status: "failed"` 和 `resultText`。完成标准：`pytest` 通过，`bun run build` 成功，浏览器预览检查对话和设置页面。
5. 实验系统接入前端。主智能体先把接口结构写入 `frontend/src/types.ts`。I 负责 `backend/harnessing_ts/experiments_api.py` 和路由注册，J 负责 `frontend/src/experiments.ts` 和页面入口。完成标准：测试中用假的 loop 命令验证启动、停止和断点续跑；浏览器预览中用 p2-3seed 数据检查展示；不发起真实的 LLM 实验。

**冲突和错误的处理**

- 同一阶段内子智能体负责的文件互不重叠。需要修改范围外的文件时，先报告主智能体。
- 发生冲突时以本文件和固定的接口为准。
- 子智能体产出有错误时退回原子智能体修改；修改两次仍未解决时，由主智能体拆分任务或自己处理。
- 每个阶段结束时由独立子智能体做静态评审（不运行测试），通过后提交并打标签。
